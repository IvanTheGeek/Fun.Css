# NEXUS Git Workflow

Full traceability — no progression, decision, or experiment lost.

## Rules

Each rule is phrased *WHEN <trigger> DO <action>* so the trigger is part
of the rule. A new session reading this should be able to map a current
situation to an action without inferring.

- **WHEN starting non-trivial work** → create a branch using a prefix
  from the *Branches* table. Never commit non-trivial work directly to
  `main`; direct commits to `main` are only for single-commit trivial
  fixes.
- **WHEN you have any change worth keeping** → commit it. Small commits
  capture the progression of thought, not just the end state.
- **WHEN merging a branch into `main`** → always use `--no-ff`
  (preserves branch topology so each body of work is identifiable as a
  unit; revertible via `git revert -m 1 <merge>`).
- **WHEN a merged branch is no longer wanted** → delete it (local +
  remote) — but only as a **separate, confirmed** step, never automatic.
  See *Feature-complete checklist*.
- **NEVER rewrite pushed history** — no `rebase` of pushed commits, no
  `--amend` of pushed commits, no `push --force`.

## Per-turn invariants

The Stop hook commits and pushes the current branch at the **end of
every turn**, so the branch state matters every turn — not just at
session start. Before any git action in a turn:

1. **Confirm the current branch name matches a prefix from the
   *Branches* table.** The harness sometimes creates auto-named branches
   (e.g. `claude/<adjective>-<surname>-<hash>`) for worktrees; those
   don't match the prefix table and will silently get pushed by the
   hook each turn. Surface mismatches and offer to rename before
   committing.
   ```
   git branch --show-current   # must match ^(feature|fix|experiment|docs|refactor|chore)/
   ```
2. **Confirm it's the intended branch.** Branches carry over between
   sessions; the hook doesn't care which one you're on.

## Branches

| Prefix | Use for | Merges to |
|---|---|---|
| `feature/` | New capability | `main` |
| `fix/` | Bug fix | `main` |
| `experiment/` | Uncertain-outcome exploration | `main` or `graveyard` |
| `docs/` | Documentation only | `main` |
| `refactor/` | Restructuring with no behavior change | `main` |
| `chore/` | Maintenance, housekeeping, convention sweeps, dep bumps | `main` |

**Permanent:** `main` (always working, integration target) and
`graveyard` (long-running archive for abandoned/failed work; never
merges back to `main`; the merge commit message must explain *why*
abandoned).

## Operational mapping — common phrasings → actions

User language is ambiguous. The same phrase can mean checkpoint or
publish depending on where the work is. Map intent before acting; ask
if unclear.

| User says | Branch state | Action |
|---|---|---|
| "commit and push" | mid-work on any branch | commit changes, push the branch (matches the Stop hook) |
| "commit and push" | finished work, ready for CD | **ask** — checkpoint-push or merge-to-main? |
| "merge to main" / "ship this" / "publish" | feature branch ready | *Feature-complete checklist*, **steps 1–4 only** (publish; branch stays alive) |
| "push and delete" / "merge and delete branch" | merged feature branch | *Feature-complete checklist*, **all steps** |
| "delete the branch" (after a prior merge) | branch already merged | checklist steps 5–7 only, with confirmation |

**Default**: when the user says "merge to main" without specifying the
branch's fate, **keep the branch alive**. Merging is the CI/CD trigger,
not the branch-is-done signal — see the *Feature-complete checklist*
rationale below.

## Feature-complete checklist

The merge-to-main step and the branch-cleanup step are **separate
operations**. Steps 1–4 are the publish step (triggers downstream CD).
Steps 5–7 are the cleanup step — opt-in, requires explicit instruction
or confirmation.

```
# Publish — merge to main, push main, keep branch alive
1. cd <main worktree>
2. git checkout main
3. git merge --no-ff <branch> -m "<message explaining what and why>"
4. git push origin main

# --- stop here by default ---

# Cleanup — opt-in only; requires explicit instruction or confirmation
5. git branch -d <branch>
6. git push origin --delete <branch>
7. git worktree remove <worktree path>          # if applicable
```

**Before any cleanup step**, run `git worktree list | grep <branch>` —
if any other worktree is checked out on this branch, do **not** delete
without surfacing that.

**Why keep the branch alive by default**:

1. **Merging is a CI/CD trigger, not a done signal.** A common pattern
   here is to keep working on the same feature branch across multiple
   merges-to-main — each merge publishes a checkpoint that kicks off
   the downstream deploy pipeline. New branch per merge would be churn.
2. **Deleting is destructive.** Remote branch delete is irreversible
   without finding the SHA elsewhere. Confirm before acting (per global
   CLAUDE.md: *"Confirm before destructive or irreversible actions"*).
3. **Other worktrees may still be on it.** Deleting a branch that's
   checked out in another worktree fails noisily but is worth checking
   up front.

## Commit messages

Prefix with one of the following, using the **full word** spelled
out exactly as listed (not abbreviated):

| Prefix | Use for |
|---|---|
| `feature:` | New capability. **Not `feat:`** -- this workspace uses the full word. |
| `fix:` | Bug fix |
| `docs:` | Documentation only |
| `refactor:` | Restructuring with no behavior change |
| `test:` | Test additions or changes |
| `chore:` | Maintenance, housekeeping, convention sweeps, dep bumps |
| `experiment:` | Uncertain-outcome exploration |
| `graveyard:` | Recording abandoned work on the `graveyard` branch |

The full-word convention (e.g., `feature:`, `refactor:`) is
deliberately chosen over the Conventional Commits abbreviations
(`feat:`, `ref:`) for readability and to match the branch-prefix
table above (`feature/`, `refactor/`, ...). Other workspaces / repos
may use the abbreviated forms; in DEVELOPMENT/, always use the full
word.

Subject under 72 chars. Add body when *why* isn't obvious from the
code.

Claude-authored commits should explain *what changed and why* — the
Stop hook's `chore: turn-end safety net` is the low-quality fallback;
do better when committing intentionally.

## Auto-commit hook — safety net, not publish

Each project's `.claude/settings.json` Stop hook fires at the end of
every turn (when Claude finishes responding); it commits any
uncommitted changes and pushes the current branch. Skips when there is
nothing to commit. Safe because you are always on a feature branch.

**Role of this hook: safety net for in-progress work.** Nothing is
lost between turns; mid-feature commits stay on the feature branch and
on the remote. **The hook is NOT the merge-to-main mechanism.** When
work reaches a publishable checkpoint, follow the *Feature-complete
checklist* explicitly — the hook will not promote work to `main` for
you.

## Integration model

No PRs — direct merges to `main` with `--no-ff`. CI here means
*continuous integration* in the original sense (small branches merged
often, history preserved), not "pull request". Each merge-to-main is
expected to trigger downstream CD; this is why the *Feature-complete
checklist* separates publish from cleanup.

## Session start

Confirm your current git branch before any work. The Stop hook commits
at the end of every turn on whatever branch you're on, so the branch
from the last turn of the previous session carries over. Make sure
it's the intended branch (never `main` for non-trivial work).

This is the one-time check at session start; the *Per-turn invariants*
section above is the recurring version that catches mid-session branch
changes and auto-named branches.

# Unicode policy for source files

The workspace allows non-ASCII Unicode in source files written or
edited by AI agents, with one absolute exception: the 16 invisible
codepoints that comprise the Trojan Source attack surface
(CVE-2021-42574 + invisible companions). Those are banned outright,
enforced by `tools/check-trojan-source.sh` via the pre-commit hook.

This is a deliberate relaxation of an earlier ASCII-only convention,
which proved too strict in practice. See decision
[`019e2e55-5cec-...`](../decisions/adopt-ascii-only-as-the-workspace-source-file-convention.md)
(the original policy, now superseded) and decision
[`019e2f13-45ab-7839-a84f-30c1885d557a`](../decisions/relax-to-bidi-controls-only-unicode-policy-supersedes-ascii-only.md)
(this policy, the supersession) for the reasoning trail.

## Rule

Source files written or edited by AI agents may contain any Unicode
character **except** the 16 codepoints in the security floor:

| Range / point | Count | What |
|---|---|---|
| U+202A through U+202E | 5 | LRE, RLE, PDF, LRO, RLO (bidi formatting) |
| U+2066 through U+2069 | 4 | LRI, RLI, FSI, PDI (bidi isolates) |
| U+200B through U+200F | 5 | ZWSP, ZWNJ, ZWJ, LRM, RLM |
| U+FEFF | 1 | BOM / ZWNBSP |
| U+061C | 1 | ARABIC LETTER MARK |
| **Total** | **16** | invisible / control codepoints with zero legitimate use in this workspace |

Everything else is permitted, including:

- Em dash (U+2014), en dash (U+2013), ellipsis (U+2026)
- Arrows (U+2190..U+2199, U+27F6, etc.)
- Math operators (U+2264, U+2265, U+00D7, U+2212, ...)
- Smart quotes (U+201C/U+201D, U+2018/U+2019)
- Section sign (U+00A7), bullet (U+2022)
- Check marks, ballot boxes, status emoji
- Diacritics in proper names
- CJK / Cyrillic / Greek / any script
- Anything else not on the 16-codepoint banned list

## What this means in practice

- **Use whatever typography is natural.** Em dashes for asides, en
  dashes for ranges, smart quotes if you prefer them, math operators
  as written. The model's typography defaults are fine.
- **Forgejo will sometimes show "ambiguous Unicode" banners.** That
  warning's set is broader than this policy (it flags U+2013 EN DASH,
  U+00D7 MULTIPLICATION SIGN, U+2212 MINUS SIGN, plus letter
  homoglyphs from UTS #39). Those characters are NOT banned by this
  policy. The banner is informational; ignore it for prose typography.
  See [`forgejo-ambiguous-unicode.md`](forgejo-ambiguous-unicode.md)
  for the exact Forgejo flag list and rationale.
- **The security floor is non-negotiable.** Any commit containing one
  of the 16 banned codepoints fails the pre-commit hook (and the Stop
  hook for agent commits). That's the whole enforcement surface
  for this convention -- there is no broader style check.

## What is enforced, and how

| Layer | Codepoints | Enforcement |
|---|---|---|
| Hard floor (this policy's only rule) | 16 invisible / control | `tools/check-trojan-source.sh` -- fails commit on detection. Wired into every workspace repo via `core.hooksPath` (set by `admin/git-repo-shape-check.sh`). Also gated in the Stop hook. |
| Forgejo ambiguous Unicode | ~1,618 (en-US locale) | Not enforced. Forgejo displays the warning in its file viewer; it does not block commits. Treat as informational. |
| Visible typography | All non-control Unicode | Not enforced. Allowed at author / editor discretion. |

## Exceptions to the security floor

There are no standing exceptions. The 16 codepoints have zero
legitimate use in this workspace's scope (English/Latin script, no
RTL text authoring, no emoji-ZWJ sequences in source).

If a future project genuinely needs to include one of these codepoints
(e.g., test fixtures that exercise bidi behavior), the right path is:

1. File a decision event under `LOGOS/decisions/` proposing the
   exception with rationale.
2. Implement the exception as a path-pattern allowlist in
   `tools/check-trojan-source.sh`, scoped narrowly (specific files,
   not "anywhere under this dir").
3. Update this convention doc to describe the exception.

Bypassing the hook (e.g., `git commit --no-verify`) is never the
correct response.

### Upstream snapshots that contain banned codepoints

When an upstream reference file (e.g., the Unicode
`emoji-data.txt`) contains a banned codepoint as a glyph sample in
its own documentation, the file is **not pinned** to `LOGOS/refs/`.
A companion documentation file is written there instead, citing the
upstream URL and providing a fetch-on-demand command. See decision
[`019e2f63-...`](../decisions/upstream-files-that-violate-the-security-floor-stay-network-fetched-not-pinned-in-logos-refs.md)
for the full rationale.

This sub-policy preserves the floor's uncompromised status without
losing the documentation value of the upstream file. The exception
procedure above (allowlist + decision event) remains available for
genuine need cases (test fixtures, research) but is deliberately
not invoked for snapshot convenience.

## Why this is the policy, not stricter

The earlier ASCII-only convention banned everything above U+007F. It
was retroactively swept across the workspace (~1,000 typography
substitutions in ~76 files), lasted briefly, and was reversed. The
trade-offs made it untenable in practice:

- Forced ASCII checkboxes (`[x]`/`[ ]`) into status tables that read
  much better with `OK`/`BAD` glyphs.
- Required mechanical translation of every em dash, ellipsis, arrow,
  inequality, math operator across all AI-authored files. Sweep cost
  was high; ongoing enforcement cost was higher.
- Gave AI agents a counterintuitive instruction (training data is
  full of polished typography) that they had to be reminded of in
  every editing session.
- Provided no security benefit beyond what the 16-codepoint floor
  already provides. The bidi/invisible attack surface is what's
  dangerous; em dashes are not.

The reversed policy keeps the security guarantee, drops the style
overhead, and frees agents to write naturally. The Forgejo banner
remains informational and tolerable.

# Workspace AGENTS.md mirroring into subproject repos

The workspace AGENTS.md (`/home/ivan/DEVELOPMENT/AGENTS.md`) does not
auto-load in sessions whose CWD is inside a subproject with its own
`.git` (LaundryLog, Fun.Blazor, Fun.Css). Claude Code's `@import`
resolver silently drops imports whose resolved target sits outside the
current project root, and `/home/ivan/DEVELOPMENT/CLAUDE.md`'s
`@AGENTS.md` resolves to a file outside any subproject's root.

The observation is recorded at
[`LOGOS/observations/019e31b7-bed0-7538-9bd5-a7ac4371ba2e.toml`](../observations/019e31b7-bed0-7538-9bd5-a7ac4371ba2e.toml);
the decision driving this convention is at
[`LOGOS/decisions/019e31d8-62ec-7663-90f2-2942da2e10ca.toml`](../decisions/019e31d8-62ec-7663-90f2-2942da2e10ca.toml).

## Mechanism

Each subproject root holds a committed `WORKSPACE-AGENTS.md` file: an
auto-generated header plus a flat copy of the workspace AGENTS.md (with
its own `@-imports` recursively inlined at sync time). Because the
mirror sits *inside* the subproject's project root, `@WORKSPACE-AGENTS.md`
from the subproject's own AGENTS.md DOES expand -- the boundary guard
that silently drops cross-root imports is satisfied.

Each subproject's `AGENTS.md` is structured as a single import line
followed by project-specific content:

- Line 1: the literal import `&#x40;WORKSPACE-AGENTS.md`
- Line 2: blank
- Line 3+: project-specific rules, headings, etc.

Each subproject's `CLAUDE.md` remains the usual one-liner: the literal
import `&#x40;AGENTS.md`.

The chain inside a subproject session is `CLAUDE.md` → AGENTS.md →
WORKSPACE-AGENTS.md (flat workspace content) plus project-specific
content from the subproject's own AGENTS.md.

(Note: the `@` characters in the example imports above are escaped as
HTML numeric character references. Bare `@`-prefixed lines inside this
convention doc would be inlined as real imports by the sync script and
re-interpreted by Claude Code's loader; the escapes keep the examples
inert.)

## Why the mirror is inline-expanded

Workspace AGENTS.md itself uses `@-imports` for its cross-cutting
conventions (e.g., `@LOGOS/conventions/WORKFLOW.md`,
`@LOGOS/conventions/unicode-policy.md`). If the mirror copied those
lines verbatim, the same boundary bug would re-bite at the second
level: the subproject's loader would try to resolve those paths
against the subproject's own root, where they do not exist, and
silently drop them.

The sync script therefore recursively inlines every `@<path>` line in
the source AGENTS.md at sync time. The resulting mirror is a flat
self-contained file with no further imports for Claude Code to resolve.

## The sync rule

**After editing workspace AGENTS.md (or any file it `@-imports`,
transitively), run `tools/sync-workspace-agents.sh` and commit each
regenerated `WORKSPACE-AGENTS.md` in its subproject repo.**

- The sync is one-way: workspace -> subprojects. Never edit a
  `WORKSPACE-AGENTS.md` directly; its auto-gen header documents the
  source and edits would be overwritten on next sync.
- The script reads source from `${script_dir}/../AGENTS.md`, so the
  *canonical* invocation is from the main worktree at
  `/home/ivan/DEVELOPMENT/tools/`, post merge-to-main. Running from a
  feature-branch worktree picks up the worktree's branch-local
  content, which is what you want for a bootstrap commit but usually
  not for an ongoing edit cycle.
- The subproject mirror writes commit in each subproject's own git
  repo, not in the workspace repo. Each affected subproject needs its
  own feature branch and commit per the workspace WORKFLOW rules.

## Discovery and idempotence

The sync script discovers subprojects by globbing direct subdirs of
`/home/ivan/DEVELOPMENT/` and including any with a `.git` file or
directory. Hidden directories (`.claude/`, `.git/` itself) are excluded
by default bash globbing rules. New subprojects are auto-picked-up on
the next run; no explicit list to maintain.

The script is idempotent -- mirrors whose contents already match the
freshly-rendered output are reported as `unchanged` and not rewritten,
so mtimes stay stable and pre-commit hooks don't re-trigger.

## Why this over alternatives

The decision event captures the full comparison. Briefly:

- **Symlink** -- likely fails because the boundary check is probably
  realpath-resolved.
- **Global SessionStart hook** -- single source of truth and no
  per-project files, but hook misfires are indistinguishable from
  the bug we're fixing; harder to debug than a script you can run
  by hand and `diff`-check.
- **Move rules to `~/.claude/CLAUDE.md`** -- loses workspace
  scoping; rules reference workspace paths (`LOGOS/`,
  `tools/check-trojan-source.sh`) that only make sense inside
  `/home/ivan/DEVELOPMENT/`.
- **Inline duplicate content in every subproject** -- heaviest
  drift surface, worst long-term.
- **Explicit Read directive on first turn** -- relies on the
  model to follow it every time; first turn has incomplete context.

## When NOT to run the script

- Mid-feature work in a workspace worktree: your worktree's
  AGENTS.md hasn't reached main yet. Running the script propagates
  branch-local content to subprojects, which is usually wrong.
  Wait until merge-to-main, then sync from the main worktree.
- The bootstrap commit (the one that adds this mechanism) is the
  one explicit exception: script + convention + initial mirrors all
  land together, with the per-subproject mirror commits parallel to
  the workspace commit.

## Verify before claiming — REQUIRED before any LOGOS write

Before any "removed" / "moved" / "deprecated" / "added in vX" /
"this works" / numeric / quantitative claim lands in **any** LOGOS file
(`libs/`, `methods/`, `decisions/`, `conventions/`, `audits/`,
`projects/`, `refs/`): verify with concrete evidence first.

Verification methods, by claim type:

- **API claims** (type exists, member moved, class removed): grep the
  shipped NuGet XML doc with `tools/nuget-xml.sh <package> <version> <pattern>`,
  or run the assembly probe documented in `LOGOS/conventions/FSHARP.md`
  → "Verifying a NuGet package's public API"
- **Behavior claims** (this code does X): sample compile / sample run /
  read the official changelog
- **Numeric or quantitative claims** (file size, type count, latency,
  version count): actual measurement, not estimation

First-pass diagnoses are **hypotheses**, not facts. Compile errors,
training-time recall, and pattern-matched intuitions are signals to
investigate — not facts to record. Unverified claims that genuinely
must go in (e.g., a starter doc with no project history yet) must be
marked inline ("speculation pending verification" or similar) so
readers know to treat them as hypotheses.

Confidently-wrong LOGOS entries are the most expensive class of error
because future sessions trust them. The cost of recovering from a
wrong claim is much higher than the cost of verifying it first — the
asymmetry favors verifying.

## Decision / observation / finding recording — REQUIRED format

Before creating any file under `<project>/LOGOS/decisions/`,
`<project>/LOGOS/findings/`, `<project>/LOGOS/observations/`, or any
workspace `LOGOS/` event-sourced folder (decisions, observations,
questions, references, experiments, corrections): **read
`LOGOS/methods/event-sourcing-as-knowledge-store.md` first**.

Format is **TOML + UUIDv7** (`<type>/<uuidv7>.toml`):

- No type prefix in filename — the folder carries the type
- No descriptive slug — identity is the UUIDv7, content is inside
- Status is a projection (computed from later events), not a stored
  field edited in place
- The view layer projects TOML events to readable markdown — humans
  read views, source files are write-only in practice
- Numbered ADR conventions (`0001-...md`, `ADR-NNN-...md`) are
  explicitly NOT used in this workspace — they conflict with the
  immutability and identity model in the methodology

Industry-standard ADR markdown is the wrong autopilot here. If you find
yourself defaulting to numbered/named markdown for any decision-class
file, stop and read the methodology.

## Library usage protocol — REQUIRED before and after using any library

**Before importing, calling, or adding any library (NuGet, npm, or
otherwise): check `LOGOS/libs/` for that library's notes file, and read
it first if present.**

Locations:

- Single-file form: `LOGOS/libs/<lib-name>.md` (e.g., `cscheck.md`,
  `verify.md`)
- Multi-topic form: `LOGOS/libs/<lib-name>/<topic>.md` (e.g.,
  `fun-blazor/styling.md`)

If a file exists: read it first. It contains accumulated project findings
— APIs, gotchas, errors with fixes, version-specific quirks. Skipping it
means re-learning lessons already paid for.

If no file exists: this is the first workspace session using that
library. Create the file as you work, following the shape of existing
libs files: header (NuGet, version, link) → when to use → API surface →
errors encountered → updating-this-file footer.

**After any session that touched a library: update that library's file.**

- New API patterns → relevant section
- Errors hit + their fixes → `## Errors Encountered` using
  `**Cause** / **Fix**` format (match existing files)
- Version changes, API surface changes → relevant section, noting the
  version
- Append-only — don't remove prior entries unless verified to be obsolete
  (e.g., fixed in a newer version)
- **Cross-write** when an error has BOTH a library angle AND a language
  angle (e.g., F# CE behavior triggered by Hedgehog `property { }` body)
  — append to BOTH `libs/<lib>.md` AND `conventions/<lang>.md` so it's
  discoverable from either entry point

**`libs/<lib>.md` is the authoritative source** for this workspace —
read it first (per the protocol above), and every outside-research
round should grow it. The goal is for `libs/<lib>.md` to be sufficient
for any agent working in the project; outside sources are fallbacks
when our own ref doesn't yet cover what's needed.

When `libs/<lib>.md` doesn't cover it, fall back to outside sources in
**cost / value order** (lowest cost and best information density first):

1. **NuGet cache XML doc** at `~/.nuget/packages/<id>/<version>/lib/<tfm>/*.xml`

   informative when present and complete. **Caveat**: XML doc
   generation is opt-in by package authors — entries can be missing
   for undocumented members, and the file may not exist at all. Use
   the XML doc to verify or extend our `libs/<lib>.md` ref, not as
   ground truth on its own.
2. **Official docs site** — narrative/usage examples that XML doesn't
   carry, but may not match your pinned version (especially for older
   or overlay versions).
3. **GitHub repo** — README, source, examples, issues. Best for
   changelogs, breaking-change announcements, and "is this fixed yet"
   questions. Network cost; navigation overhead.
4. **Web search** — last resort. Third-party content, version-fluid,
   signal/noise low.

**Never guess from DLL structure or training-time knowledge** —
guesses produce wrong code. Capture what you learned in the libs file
as part of the after-session update, so the next session doesn't have
to repeat the search.

**Verify before claiming** applies to every libs/ write — see the
top-level "Verify before claiming" section for the full directive.

This is how `LOGOS/libs/` grows. Without it, every session re-discovers
the same gotchas.

## .NET / NuGet packaging — REQUIRED before adding packages or editing nuget.config

**Before adding a `PackageReference`, creating a project, or modifying
`nuget.config`: read `LOGOS/conventions/nuget-feeds.md`.**

The workspace uses three NuGet feeds (`nuget.org`, `FnTools`,
`IvanTheGeek`) and overlays specific public packages (currently
`Fun.Blazor`, `Fun.Blazor.Server`, `Fun.Css`) with workspace builds that
carry fixes ahead of upstream. The required `nuget.config` template and
the per-package version patterns (e.g., `4.1.10-IvanTheGeek.*` rather
than `4.*`) live in that conventions file. Default floating-version
patterns silently resolve to upstream public versions and miss the
overlays.

**Before any `PackageReference` or `#r "nuget: X"` lands** (in
`.fsproj`, `.csproj`, `.fs`, or `.fsx`): verify the public API at the
version you'll resolve to. The shipped XML doc at
`~/.nuget/packages/<pkg>/<version>/lib/<tfm>/*.xml` is the authoritative
API surface for that version. Use `tools/nuget-xml.sh <package> <version> <pattern>`
to grep it, or `--surface` for the full type list. Training-time
knowledge can be one or two major versions stale; the 30 seconds to
verify saves compile-fix cycles AND prevents confidently-wrong API
claims from landing in `libs/<lib>.md`. The goal: get the code right
the first time.

## F# code — REQUIRED reading before any F# work

**Before writing or modifying any `.fs`, `.fsx`, or `.fsproj` file, read
`LOGOS/conventions/FSHARP.md` first.** That file (~500 lines) is the
canonical F# rulebook for this workspace and covers:

- Wlaschin / DMMF principles — illegal states unrepresentable, `Result`
  types, parse-don't-validate, railway-oriented programming
- Compiler rules — compile order, `rec` / `and`, exhaustive pattern
  matching, `namespace` vs `module`
- `<NoWarn>` and file-wide `#nowarn` policy — **prohibited**; every warning
  indicates real incorrectness, "pre-existing" is not an exemption; scoped
  `#nowarn N` / `#warnon N` pairs are the only acceptable exception
- F# 9 nullness with `System.Text.Json.Nodes` — FS3261 traps,
  `Option.ofObj` for genuine narrowing
- TOML serialization patterns for STRATUM backends (no external library;
  manual write + flat key-value parser; decimal-in-TOML round-trip rules)
- Testing stack — Expecto + Hedgehog + CsCheck (`Nexus.Modeling.Testing`
  ships the full stack)

Skipping `FSHARP.md` means rediscovering already-mapped failure modes
(FS3261 nullness traps, file-wide `#nowarn` anti-patterns, decimal-in-TOML
round-trip breakage, custom-op visibility issues, etc.).

**After any F# work session: update `FSHARP.md` with new findings.**

- New errors hit + their fixes → `## Errors Encountered` using
  `**Context** / **Cause** / **Fix**` format (match existing entries)
- New compiler quirks, language-version surprises, pattern discoveries
  → relevant section
- Append-only — don't remove prior entries unless verified to be obsolete
  (e.g., fixed in a newer F# release)

## Editing practices

- **Inspect → change → verify** — read the actual current state before
  editing; verify the result after. Never assume or guess what is current.
- **Cross-file renames / string replacements** — grep the full tree first to
  find every occurrence; apply changes to all matching files at once; grep
  again after to confirm zero remaining occurrences.
- **UI components — design system first** — never invent class names,
  layout, states, or tokens; the design system specifies them.
- **Unicode allowed except the 16 invisible Trojan Source codepoints** —
  use whatever typography reads naturally (em dash, smart quotes,
  arrows, math operators, etc.). Only the bidi-control + invisible
  codepoints (CVE-2021-42574 + companions) are banned, enforced by
  `tools/check-trojan-source.sh` via the pre-commit hook. See
  `LOGOS/conventions/unicode-policy.md` for the full rule, the exact
  16 codepoints, and the trade-offs behind this policy.
